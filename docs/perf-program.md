# Kivi performance: method and current results

This document describes **how to measure Kivi and what it currently costs**. It is
not a journal. Measurements that no longer describe the code have been removed;
the reasoning that led to the current design is in Git.

Read [`microscope.md`](microscope.md) first. It records what this host can
actually measure, and that determines what any number here is allowed to mean.

## 1. The instrument

`crates/kivi-wirelab` runs a client and one server per target, in separate
processes, and accounts for both wall and CPU time from `/proc`:

| target | what it is | why it exists |
| --- | --- | --- |
| `a` | raw compio echo | the floor: what the round trip costs with no server logic |
| `c` | RESP parse + in-memory table | **the control.** A correct minimal implementation of the same semantics |
| `d` | production `kivi-server` | the thing under test |
| `redis` | Redis 8.10.1, same machine | an external reference, not a target |

`c` is the number that matters. `d − c` is Kivi's architecture tax, isolated from
the round trip, the CPU, and the client. Kivi-versus-Redis is a marketing number;
`d − c` is a design number.

Two methodological rules, both learned the hard way:

- **One client, one payload, one key distribution, one pipeline depth, one
  durability class.** A comparison that varies more than one of these measures
  the variation.
- **The round trip is not Kivi.** On this host it is ~24 µs, and it is a WSL2
  virtualised-loopback number, not a property of the server. That is why `a`
  exists. Any conclusion drawn from a p1 wall-clock number is a conclusion about
  the round trip.

## 2. The microscope

`crates/kivi-microscope` reports instructions (callgrind) and time (TSC). Three
constraints on this host, which bound what may be claimed:

1. **No hardware PMU.** Instruction counts come from callgrind and time from the
   TSC. The two are never substituted for one another.
2. **The TSC is a clock, not a cycle counter** - 0.69–0.73 core cycles per tick,
   and it moves with turbo. A cycles-per-instruction figure requires a
   per-run calibrated ratio with its spread reported.
3. **`rdtsc` costs 6 ns**, about 3% of a `GET`. Measurement boundaries are
   adjacent, opt-in, and checked against a baseline for the overhead they add.

`ptrace_scope=1` on this host: neither `strace -c -p` nor `valgrind --pid` can
attach to a sibling process, so a server under measurement must be *launched*
under the tool rather than attached to. `strace` also inflates the round trip
4.5×, which makes it useless for latency and fine for syscall counts.

## 3. What Kivi costs now

Pipeline 256, `GET` of a 16-byte resident value, min of 5, clean preflight. The
full matrix is regenerated by:

```sh
cargo build -p kivi-server --release
cargo build -p kivi-wirelab --release
python3 crates/kivi-wirelab/lab.py \
    --shapes 1:1,1:4,1:16,1:64,1:256 --blocks 1200 --repeats 5 \
    --targets a,c,d,redis
```

| target | wall ns/op | CPU ns/op |
| --- | ---: | ---: |
| `a` raw echo | 109 | 52 |
| `c` control | 186 | 137 |
| **`d` production** | **201** | **163** |
| `redis` 8.10.1 | 295 | 273 |

**`d − c` is 15 ns/op wall and 26 ns/op CPU.** Production is 32% faster than Redis
at this depth. Zero protocol errors at every pipeline depth.

For reference, `d − c` was 372 ns/op wall and 488 ns/op CPU before the direct
execution path, and 4,087 instructions per pipelined `GET` rather than 1,340.

### At lower depths the round trip dominates

| pipeline | `a` | `c` | `d` | `redis` |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 23,523 | 24,756 | 25,798 | 25,699 |
| 4 | 6,099 | 6,443 | 6,574 | 6,969 |
| 16 | 1,553 | 1,698 | 1,755 | 1,904 |
| 64 | 401 | 492 | 516 | 628 |
| 256 | 109 | 186 | 201 | 295 |

At p1 the three-way spread between `a`, `c` and `d` is ~1.3 µs on a 25 µs request.
Kivi is not what a p1 client is waiting for.

## 4. Where the remaining instructions go

Per pipelined `GET`, by running the server under `valgrind --tool=callgrind`
while a fixed number of commands is issued, and attributing the resulting
`callgrind.out` with `callgrind_annotate --inclusive=no` to Kivi's own symbols.
Divide by the command count. Reproduce with:

```sh
valgrind --tool=callgrind --callgrind-out-file=cg.out \
    target/release/kivi-server --ephemeral --workers 1 --tablets 1 \
        --redis-listen 127.0.0.1:7401 --no-checkpoint --placement none &
# issue a known number of GETs, then:
callgrind_annotate --inclusive=no cg.out
```

Attribution to a *stage* rather than a symbol is manual: each row below is the sum
of the functions that do that stage's work, and the stage names are chosen so the
row changes when the stage's implementation changes. Two numbers here are worth
stating how they were obtained, because they are the ones that would otherwise be
taken on trust:

- **the fast-path hit rate.** Not instrumented. The general path's functions
  (`command::lookup`, `translate`, `run_batch`) are absent from the profile, which
  means they executed zero instructions across 15,360 commands, which means every
  command took the direct path.
- **the allocator's `realloc` share.** Not from the symbol list, which shows only
  `malloc`/`free`; it comes from the call graph in `cg.out`, which attributes
  `__rdl_realloc` and `_int_realloc` edges to their callers.

| stage | Ir/cmd | share | note |
| --- | ---: | ---: | ---: |
| `parse_command` | 347 | 25.9% | largest single item |
| `__memcpy_avx_unaligned_erms` | 217 | 16.2% | not yet attributed by site |
| `fast_prefix` | 137 | 10.2% | the direct path's own body |
| `_int_malloc` | 102 | 7.6% | **realloc**, not malloc - see below |
| `fold_command_name` | 70 | 5.2% | uppercases the name per command |
| `fast_read` | 69 | 5.1% | |
| `ObjectStore::get_borrowed` | 67 | 5.0% | one probe |
| `write_bulk` + `write_usize` | 108 | 8.1% | reply framing |
| `ahash::hash_one::<&[u8]>` | 45 | 3.4% | the store's own table hash |
| `free` + `_int_free_merge_chunk` | 67 | 5.0% | |
| **total attributed** | **1,340** | | |

Absent entirely, and worth keeping absent: the crossbeam rendezvous, the
`translate`-to-`Operation` step, `__divti3`, and any `TabletId` hash. The direct
path's general-route fallback executed **zero** instructions across the whole
profile, so the fast-path hit rate is 100% - inferred from machine work rather
than from counters.

## 5. The two things to attack next

**The allocator is `realloc`, which is a bug, not an optimisation.** Allocating
call-graph edges per command:

| edge | Ir/cmd |
| --- | ---: |
| `__rdl_realloc` | 101 |
| `_int_realloc` | 42 |
| `__libc_malloc2` | 83 |

A steady-state `GET` should allocate nothing. It certainly should not *grow* a
buffer per command. The reply buffer is already reused and cleared, so the growth
is in a buffer that was believed to be reused and is not. Find it before
optimising anything else.

**Then the parser.** `parse_command` plus `fold_command_name` is 417 Ir/cmd, 31%
of the path, spent turning sixteen bytes of RESP into a command name. While the
round trip dominated, that was 0.14% of what a client saw and the right call was
to leave it alone. With the tax gone it is the binding constraint. The shape of
the work is a parser that emits a borrowed command reference and never
materialises an `Operation` for a command that does not need one, followed by a
vector executor that parses, hashes, routes, prefetches and probes *N* commands
across a pipeline rather than one at a time.

## 6. Settled, and not to be reopened without new data

| question | answer | why |
| --- | --- | --- |
| route hash | `kivi_state::route_hash`, XXH3-128, namespace-derived seed | stable and public; routing needs no cryptographic strength |
| table hash | `ahash::RandomState`, held per store, never persisted | the table is not a trust boundary; the key is the only untrusted input and it is the only thing hashed. The store's `RandomState` has a non-leaking `Debug`, so no key material can reach a log through a bucket value |
| one hash for both | rejected | the requirements are independent, so a shared hash couples them |
| a second route construction | **removed** | it existed, and it was not cosmetic - see below |
| constant single-tablet route | in production | a one-tablet namespace routes to a constant; the hash has no consumer |
| compiled routing | `LocalRoutes` → `LocalTabletSlot` | a request indexes a `Vec` instead of hashing a `TabletId` |
| custom reactor | rejected | the compio control already beats Redis; the cost was above the runtime, not in it |
| digest remix | rejected | the premise is false on this host |

XXH3-128 is cross-checked against upstream's own test vectors, and pinned by a
frozen table in `kivi-state`. Those vectors are a wire/persisted contract and are
kept.

### The second construction was a live bug, not a latent one

`kivi_state` carried a `PartitionHasher` enum selecting between BLAKE3-128 and
XXH3-128, and while it did, **nine production sites computed a routing identity
with BLAKE3** - the client (5), the cluster edge (2), the control plane, the
split planner - while the engine routed with XXH3.

The client was the visible symptom. It keyed its route cache on the BLAKE3
identity, which the server never produced, so **every lookup missed**:
`route_miss_redirects_then_goes_direct` measured 21 redirects where 1 is
correct. The same divergence meant a key resolved to a different tablet depending
on which of two routers ran.

The enum is gone. `kivi_state::route_hash` is the only function that turns key
bytes into a routing identity; it is infallible, so the `Option` and the
`UnsupportedHash` error variant went with it. The checkpoint's band index - whose
own comment already demanded that "band identity must be as stable as the
partition hash itself" while deriving it from the *other* hash - now uses it too.
`BLAKE3` remains in the tree for content-addressing checkpoint artifacts, which is
a different question from routing a key.

The lesson is the one the module already warned about and did not apply: *"a hash
with two spellings is a hash whose two callers can disagree."* Nothing in the type
system objected, because both spellings returned a `PartitionHash`.

## 7. Rejected: one hash construction

A KiviHash V2 construction (AES-based, Davies–Meyer-style) was prototyped,
measured at 5.2 ns for a 16-byte key, and **disqualified**. It is not a
Davies–Meyer compression function, its claimed security does not hold, and the
routing role it was proposed for requires no cryptographic strength anyway. The
prototype and its source file have been deleted. The disqualification reasoning
is in the commit history; the conclusion is the table in §6.

## 8. Pitfalls worth remembering

- **`/tmp` is reclaimed between WSL invocations.** Durable benchmark state goes in
  a home directory.
- **The RESP edge is a default feature**, so a plain `cargo build -p kivi-server`
  produces a working wire endpoint. It used to be default-*off*, which meant a
  benchmark could silently measure a binary with no protocol at all. A
  native-protocol-only build is still available with `--no-default-features`.
- **`cargo nextest` writes its summary to stderr.** A pipeline that reads stdout
  sees an empty result and looks like success.
- **`pkill -f <pattern>` matches the calling shell** when the pattern appears in
  its own command line. Bracket a character.
- **`$VAR` and backticks in heredocs get mangled** through nested shells. Write
  scripts to a file and invoke them by path.
- **The load average takes minutes to decay.** A benchmark started during the
  decay of a previous one is not a clean run; wait for it.
